# Adaptive Architecture — Product Audit (2026-05-18)

## What this repo's adaptive architecture actually delivers

This repository runs on a self-remediating, ownerless governance model — a control plane that lets a documentation site of nearly 800 pages keep its own house in order without a standing maintainer interpreting every drift event. Traditional docs repos depend on humans to spot stale catalogues, broken redirects, mismatched style, or out-of-date generated artefacts. This repo treats that work as a contract: every governed surface declares its canonical source, deterministic validator, exact repair command, and primary gate layer. If any of those four are missing, the surface is held in "advisory" state until the contract is complete. Once it is complete, an OSS contributor — or an AI agent acting on their behalf — can correct routine drift without privileged context or staff approval.

For a contributor, this means the failure mode of the repository is not "ask the team how to fix this". A failing check on a PR or a pre-commit hook prints why it failed, the canonical source the rule traces back to, the exact `lpd repair --surface <id>` command that fixes the deterministic part, and the re-check command that proves the fix landed. For a maintainer, it means policy authoring (in `docs-guide/policies/*.mdx`), runtime configuration (in `operations/governance/config/*.json`), and enforcement (in `.githooks/`, `tests/run-*.js`, and `.github/workflows/`) are deliberately decoupled. Policy text never embeds path logic; runtime configuration never embeds policy prose; hooks never embed rule definitions — they read the manifest.

The novelty is not the use of validators or hooks individually — most large repos have those. The novelty is the manifest-driven five-stage loop and the explicit retirement of "human-only context" as a dependency. Eight ownerless surfaces are currently declared in `ownerless-governance-surfaces.json`, twenty-eight surfaces in `repo-governance-surfaces.json`, and twenty-nine generated artefacts in `generated-artifacts.json`. Every one of those entries names its sources, its derived outputs, its validators, its repair commands, its single gate layer (`pre-commit`, `pr-changed`, `scheduled`, or `manual`), and its rollout state (`advisory`, `autofix`, `blocking`, or `migrating`). The contract is the artefact, not the person.

The loop plays out as: a validator detects drift with a precise path, rule, and severity; the policy document explains the canonical source and the reason for the rule; a remediator script or `lpd repair` command repairs only the owned surface; the validator re-runs and either passes cleanly or surfaces a smaller next failure; and a generated report, catalogue, or decision-registry entry records the change. This is intentionally designed so contributors with no prior repo context can complete the loop with only repo-local instructions — and so AI agents (Codex, Cursor, Claude, Windsurf, Augment, Copilot) can read the same six native adapter files and arrive at the same answer.

## The Control Loop in Practice

A concrete example: a contributor edits `snippets/components/elements/Badge/Badge.jsx` and forgets to update the JSDoc `@usedIn` tag.

1. **Detect.** Pre-commit runs the component metadata validator (`operations/scripts/validators/components/library/...`). It reports: file path, the missing tag, severity P2, and the exact validator command.
2. **Explain.** The hook prints a link to `docs-guide/frameworks/component-framework-canonical.mdx` (the canonical source for the 7-tag JSDoc contract) and notes that the surface is declared in `ownerless-governance-surfaces.json` under id `component-governance`, gate layer `pr-changed`, rollout state `autofix`.
3. **Repair.** The hook prints: `lpd repair --surface component-governance --write --staged`. That command runs `operations/scripts/remediators/components/library/repair-component-metadata.js` against only the staged file set. The remediator derives the missing `usedIn` field from `tools/lib/governance/component-governance-utils.js::buildComponentUsageSummary()` — a live scan of MDX imports.
4. **Verify.** The remediator includes a `--verify` mode that re-runs the validator after writing. If the validator still fails, the loop hands back control instead of escalating.
5. **Record.** The repaired file is staged for commit alongside the source change. The catalogue at `docs-guide/catalog/components-catalog.mdx` is regenerated by the same dispatch path because `generated-artifacts.json` lists it as a `committed_derived_scoped` artefact whose source set includes `snippets/components/**`. The PR body picks up the change set; the governance approval policy decides whether the `approval:governance-schema` label is required based on the surface touched.

A second example, taken from the live state of the repo today: `generate-repo-governance-status.js --check` reports `docs-guide/repo-ops/config/repo-governance-map.mdx is stale.` (Verified — this command was run during the audit and returned exactly that string.) The repair is published on the same page: regenerate the map with `--write` and commit it as a `committed_derived_scoped` artefact. The fact that this drift is sitting there now demonstrates both the strength of the model (the system reliably flags itself) and the gap (a stale generated artefact remains uncorrected because nothing yet auto-runs the repair).

## Cross-feature observations

- **Is the model actually ownerless?** Mostly yes, with caveats. Eight surfaces are formally ownerless-ready. The four-part contract is real and enforced for those. But the manifest still uses `owner: docs` everywhere in `root-governance.json`, the agent-governance taxonomy references `@livepeer/docs-team`, and several policies say "human review" or "review owner". The model is "ownerless for routine drift", not "ownerless for policy authorship or destructive operations". This distinction is consistent with the design but worth surfacing in product narrative.
- **Mature vs prototype.** Mature: validators corpus (49), remediators corpus (29), generators corpus (30), root governance pipeline, agent governance Phase 9, em-dash/spelling/page-link repair flows, generated-artifact manifest. Prototype/stub: `tasks-retention.yml` (workspace TTL), automated decision-registry enforcement, `repo-governance-map.mdx` regeneration cadence, freshness-monitor for `lastVerified`.
- **Stale generated maps.** Confirmed during this audit: `generate-repo-governance-status.js --check` prints `docs-guide/repo-ops/config/repo-governance-map.mdx is stale.` The map shows generation timestamp `2026-04-07T13:18:37.118Z` — about six weeks behind today. This is the canonical example of the gap: the system detects its own staleness, but no auto-run repairs it.
- **V2 cleanup matrix.** 307 rows backlog. 235 `_workspace` candidates, 72 `x-deprecated` candidates, 41 internal-scope rows. The largest section (`gateways`) carries 199 rows alone. The pipeline is mature (policy, lane definitions, matrix generator); execution is the gap. No automated move-waves have run; humans are expected to approve each batch.
- **218 scripts lack JSDoc compliance.** Out of approximately three hundred scripts in `operations/scripts/`, the footprint audit reports 218 fail the 11-tag template. This is a real maturity gap — the framework demands the headers, but the legacy population hasn't been backfilled. The `repair-script-inventory.js` remediator exists but has not been run at scale.

## Recommended single-page rewrite outline

Working title: **"Self-Remediating Docs Infrastructure"** (replaces the current `adaptive-architecture.mdx` headline).

1. **Hook (3 lines).** "This repo fixes its own drift. Every governed surface has a canonical source, a deterministic validator, an exact repair command, and a single gate layer. Contributors and AI agents can correct routine failures without staff context."
2. **Why this exists.** The problem with traditional docs repos: every drift becomes a staff question. Demonstrate cost: 800 pages, 45 workflows, 30 generators, 49 validators — humans cannot interpret every failure. State the design tenet: policy decisions stay human, routine drift becomes contract.
3. **The four-part contract.** Canonical source, deterministic validator, exact repair path, single gate layer. One paragraph each. Link to `ownerless-governance.mdx` for full text.
4. **The five-stage loop.** Detect → Explain → Repair → Verify → Record. One concrete example walked end-to-end (component metadata or em-dash repair). Show the actual hook output the contributor sees.
5. **What's governed today.** Three numbers: 8 ownerless-ready surfaces, 28 surfaces in the broader registry, 29 generated artefacts. Link to manifests.
6. **The script corpus.** Validators (49), Remediators (29), Generators (30), Audits (21). One sentence per family. Single `lpd repair` entry point.
7. **Rollout ladder.** Advisory → Autofix → Blocking. Migrating as transitional. Promotion criteria.
8. **Hooks, CI, and approvals.** Two-tier enforcement (hard gates + soft checks). Approval labels for governance-sensitive PRs.
9. **What's not ownerless (yet).** Policy authorship, destructive operations, retention enforcement, three identified gap areas. Honest about the line between "ownerless for routine drift" and "ownerless for everything".
10. **How to contribute.** The five-step OSS loop. Top three community-help paths (backfill headers, promote one surface, run a v2 move-wave).
11. **Related contracts.** Links to ownerless-governance, source-of-truth, infrastructure-principles, generated-artifact-and-hook-governance, agent-governance-framework, governance-index, gap-analysis.

Anchor the page so an outside contributor lands on it and understands: "this is novel; here is how to participate; here is the exact contract every change must satisfy." The current `adaptive-architecture.mdx` is correct but reads like a reference table. The rewrite should read like a product story.
