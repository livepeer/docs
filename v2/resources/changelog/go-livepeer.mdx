<Update label="Week of June 29, 2026 (start-of-week update)" tags={["Remote Signer", "Security"]} description={<Subtitle variant="changelog">June 30, 2026</Subtitle>}>
  ## Start-of-week update — June 30, 2026

### Updates

- **Remote signer now fails closed on public addresses without auth** - A remote signer bound to a non-loopback `-httpAddr` will refuse to start unless either `-remoteSignerWebhookUrl` is set or the new `-remoteSignerAllowNoAuth` flag is passed. This closes a configuration footgun where a publicly reachable signer with no webhook could be made to sign live payment tickets for any caller. Loopback bindings and deployments that already configure a webhook are unaffected; operators who intentionally run an unauthenticated public signer must now opt in explicitly. A warning is also logged whenever no webhook is configured. See the [remote signers guide](/v2/gateways/guides/payments-and-pricing/remote-signers) for setup details.

</Update>

<Update label="Week of June 22, 2026 (mid-week update)" tags={["Remote Signer", "Logging"]} description={<Subtitle variant="changelog">June 26, 2026</Subtitle>}>
  ## Mid-week update — June 26, 2026

### Updates

- **Debug logging now follows the `-v` flag** - Setting `-v 6` (the documented maximum verbosity) now also enables debug-level output from the structured logger used by the live runner, trickle, AI worker, and media subsystems. Previously those debug lines were silently dropped, making it harder to diagnose Live AI and BYOC issues. No action is required for normal operation; raise `-v` only when you need deeper logs. See the [Live AI overview](/v2/gateways/guides/node-pipelines/ai-pipelines) for context on which components this covers.

### Bug fixes

- **Remote signer mode no longer fails to start as a non-root user** - When launching a node with `-remoteSigner`, the management CLI address was unset and the node fell back to binding port 80, which fails with "permission denied" for non-root users and shut the node down on startup. The CLI address now defaults to `127.0.0.1:3935` in remote signer mode, matching the loopback default used by other node types and avoiding a port collision with a co-located broadcaster. Existing setups that explicitly pass `-cliAddr` are unaffected. See the [remote signers guide](/v2/gateways/guides/payments-and-pricing/remote-signers) for setup details.

</Update>

<Update label="Week of June 22, 2026" tags={["Release", "v0.8.11", "BYOC", "Live AI"]} description={<Subtitle variant="changelog">June 22 – 26, 2026</Subtitle>}>
  ## Week of June 22, 2026

go-livepeer **v0.8.11** shipped this week. Highlights below; see the [GitHub release notes](https://github.com/livepeer/go-livepeer/releases/tag/v0.8.11) for the full list.

### New features

- **Authenticated BYOC worker registration** - Orchestrators running Bring-Your-Own-Container workloads can now require a shared auth token when external workers register with the node. This gives operators a simple way to keep unauthorized workers from attaching to a BYOC-enabled orchestrator. Existing setups continue to work; the token is only enforced when configured. See the [BYOC tutorial](/v2/gateways/guides/tutorials/byoc-cpu-tutorial) for end-to-end setup.
- **Payment tracking events for Live AI** - Live AI gateways can now emit per-payment events to an external stream, making it easier for operators to monitor spend in real time and reconcile usage against orchestrator billing. The feed is off by default and only activates when an export target is configured. See the [Live AI payments guide](/v2/gateways/guides/payments-and-pricing/payment-guide) for background.
- **New trickle endpoint for stream continuity** - The trickle subsystem used by Live AI pipelines gained a new per-channel endpoint that lets clients pick up the next segment in a stream more reliably, improving resumption behavior for long-running realtime sessions. No configuration changes are required. See the [Live AI overview](/v2/gateways/guides/node-pipelines/ai-pipelines) for how trickle fits into the AI media path.

### Updates

- **Webcam input for the Livepeer-in-a-Box demo** - The bundled `box` demo environment now supports webcam input out of the box, making it easier for new operators to try Live AI end-to-end on a laptop without wiring up an external RTMP source. Existing demo flows are unchanged.
- **Slimmer macOS builds** - macOS binaries no longer bundle the X11 dependency, producing a smaller download and removing an unused system requirement on Mac hosts. No action required for existing installs.

### Bug fixes

- **Stricter ticket parameter validation on gateways** - Gateways now reject probabilistic micropayment tickets that advertise a zero expiration block, ensuring every paid ticket is subjected to the standard economic caps before it is accepted. Previously, tickets with a zero expiration block could bypass those caps. Honest orchestrators always advertise a non-zero expiration block, so well-behaved deployments are unaffected. Gateway operators should update to the latest build to pick up the fix. See the [payment guide](/v2/gateways/guides/payments-and-pricing/payment-guide) for background on how gateways handle orchestrator tickets.

</Update>

<Update label="Week of June 8, 2026" tags={["Live AI", "Remote Signer"]} description={<Subtitle variant="changelog">June 8 – 12, 2026</Subtitle>}>
  ## Week of June 8, 2026

### New features

- **Optional RTMP output for the AI media server** - Live AI gateway operators can now disable RTMP egress on the AI media server when it isn't needed — for example, when streams are delivered to viewers over WHEP instead of being republished as RTMP. Turning RTMP output off avoids spinning up an unused encode path, which reduces overhead for WHEP-only deployments. RTMP output remains enabled by default, so existing setups are unaffected. See the [AI pipelines guide](/v2/gateways/guides/node-pipelines/ai-pipelines) for Live AI gateway configuration.

### Updates

- **Optional auth webhook for remote signers** - Operators running a remote signer alongside a Live AI gateway can now point the signer at an external webhook to enforce policy checks before payments are signed. When configured, the signer forwards the incoming request headers and current signer state to the webhook URL and only proceeds with signing if the webhook returns a 200. Non-200 responses are propagated back to the caller with the upstream status code, making it straightforward to reject or rate-limit payment requests at the policy layer. Existing remote signer deployments are unaffected unless the new webhook URL is set. See the [remote signers guide](/v2/gateways/guides/payments-and-pricing/remote-signers) for setup details.

</Update>
