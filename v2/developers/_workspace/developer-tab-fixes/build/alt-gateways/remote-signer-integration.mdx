A remote signer is an HTTP service that generates probabilistic micropayment (PM) tickets on behalf of a gateway. The gateway sends signing requests; the signer holds the ETH keystore and returns signed tickets. This separation means the gateway process never has access to private keys.

The remote signer pattern was introduced in go-livepeer PRs #3791 and #3822, and is the recommended architecture for production gateways that handle AI inference workloads.

<CustomDivider />

## Architecture

```
Gateway (livepeer-python-gateway)
  │
  │ POST /generate-live-payment
  │   body: OrchestratorInfo, manifest_id, state
  │
  ▼
Remote Signer
  │
  │ signs PM ticket with ETH keystore
  │ returns: payment + seg_creds + updated state
  │
  ▼
Gateway
  │
  │ POST /payment (to orchestrator)
  │   headers: Livepeer-Payment, Livepeer-Segment
  │
  ▼
Orchestrator
```

The gateway carries signer state across calls. Each `generate-live-payment` request includes the current state; the signer returns updated state with the signed ticket. This round-trip keeps the signer stateless between HTTP requests.

<CustomDivider />

## Integrating with livepeer-python-gateway

The `PaymentSession` class handles the signer integration:

```python
from livepeer_gateway.lv2v import start_lv2v, StartJobRequest

job = start_lv2v(
    orch_url="https://orch.example.com:8935",
    req=StartJobRequest(model_id="streamdiffusion-sdxl-v2v"),
    signer_url="https://signer.example.com",
    signer_headers={"Authorization": "Bearer sk_xxx"},
)

# PaymentSession is created automatically
# Background payment task sends one payment every 5 seconds
```

Pass `signer_url` to `start_lv2v` and the function creates a `PaymentSession` internally. The background payment task calls `session.get_payment()` periodically, which calls the remote signer, and then POSTs the resulting headers to the orchestrator.

**Off-chain mode (no signer):** Omit `signer_url` and `start_lv2v` uses the orchestrator's `auth_token` for authentication without PM tickets. This is for development or when the orchestrator accepts off-chain payment.

<CustomDivider />

## Signer state management

The signer state (`PaymentSession._state`) accumulates nonce counters and ticket parameters across calls. Three rules:

1. Never create a new `PaymentSession` per segment. State continuity is required.
2. Never call `get_payment()` concurrently on the same session. The background payment sender serialises calls automatically.
3. If the session is dropped mid-stream and re-created, the signer starts fresh. This is valid but resets balance accrual.

On HTTP 480 from the signer (`SignerRefreshRequired`), `get_payment` re-fetches `OrchestratorInfo` from the orchestrator and retries up to 3 times.
