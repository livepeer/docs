Trickle is an HTTP-based unidirectional streaming protocol developed for Livepeer's real-time AI pipelines. It is the transport layer beneath `live-video-to-video`: when a gateway starts a real-time session, the orchestrator returns trickle `publish_url` and `subscribe_url` endpoints. The gateway publishes input frames to one URL and subscribes to output frames from the other.

The protocol is implemented in [`j0sh/http-trickle`](https://github.com/j0sh/http-trickle) (Go) and [`livepeer/pytrickle`](https://github.com/livepeer/pytrickle) (Python).

<CustomDivider />

## Publish/subscribe model

A trickle channel is a pair of HTTP endpoints:

- **Publish URL:** The producer POSTs segments to this URL. Each POST is a segment with a sequence number.
- **Subscribe URL:** The consumer GETs segments from this URL. The server holds the connection open and delivers segments as they arrive.

```
Producer (gateway)                  Trickle Server                  Consumer (orchestrator)
    │                                    │                                    │
    │── POST /publish?seq=0 ──────────►  │                                    │
    │                                    │  ◄── GET /subscribe?seq=-2 ────────│
    │── POST /publish?seq=1 ──────────►  │  ── deliver segment 1 ──────────► │
    │── POST /publish?seq=2 ──────────►  │  ── deliver segment 2 ──────────► │
```

The `seq=-2` parameter on the subscriber means "start from the latest available segment." `seq=-1` means "start from the next segment that arrives." Positive integers request a specific sequence number.

<CustomDivider />

## Protocol properties

**HTTP-only:** Trickle uses standard HTTP/1.1 or HTTP/2. No UDP, no ICE negotiation, no STUN/TURN. It works through corporate firewalls, CDN proxies, and cloud load balancers without special configuration.

**Unidirectional:** Each channel flows one way. Bidirectional communication uses two channels (one publish URL per direction). `live-video-to-video` sessions use one channel for input frames (gateway to orchestrator) and one for output frames (orchestrator to gateway).

**Segment-based:** Data is divided into segments with monotonically increasing sequence numbers. Each segment is a complete unit (typically one video frame or one audio chunk). The subscriber can request a specific sequence number or the latest/next segment.

**Lag policy:** When the subscriber falls behind, the lag policy determines behaviour. `LATEST` skips to the most recent segment (drops frames to maintain real-time). `BUFFER` delivers all segments in order (adds latency).

## Developer usage

Most developers do not interact with trickle directly. ComfyStream and PyTrickle handle the transport automatically. Direct trickle access is relevant when building custom BYOC containers or alternative gateway implementations.

The `LiveVideoToVideo` object from `livepeer-python-gateway` exposes trickle URLs directly:

```python
job = start_lv2v(orch_url="https://orch.example.com:8935", req=req)
print(job.publish_url)    # trickle publish endpoint
print(job.subscribe_url)  # trickle subscribe endpoint
```
