When a gateway receives a job, it selects an orchestrator from the network's active set. The selection process is the same for go-livepeer gateways and custom gateway implementations; the difference is whether it happens automatically (go-livepeer) or through explicit API calls (`livepeer-python-gateway`).

<CustomDivider />

## Discovery: GetOrchestratorInfo

The gateway sends a `GetOrchestratorInfo` gRPC call to candidate orchestrators. The response includes:

- Ticket parameters (sender, recipient, face value, win probability)
- Transcoder URL (where to send segments or frames)
- Supported capabilities and model IDs
- Price per unit

The gateway caches this information for the session's duration. For batch jobs, the cache lives for one request. For `live-video-to-video`, the cache persists until the stream ends or the orchestrator fails.

<CustomDivider />

## Selection algorithm

**go-livepeer (automatic):** Uses stake-weighted random selection from the on-chain orchestrator registry. Orchestrators with higher stake are more likely to be selected. The `-maxPricePerUnit` flag filters out orchestrators above the price threshold. The `-orchAddr` flag pins to specific orchestrators, bypassing stake-weighted selection entirely.

**Custom gateways (`livepeer-python-gateway`):** The `orchestrator_selector` function returns a `SelectionCursor` that batches `GetOrchestratorInfo` calls in parallel (5 at a time) and returns candidates in completion order. The caller pops candidates one at a time, trying each until one accepts the job.

```python
from livepeer_gateway.selection import orchestrator_selector

cursor = orchestrator_selector(
    orchestrators=["https://orch-1.example.com:8935"],
    capabilities=capabilities,
    use_tofu=True,
)

url, info = cursor.next()  # first available orchestrator
```

<CustomDivider />

## Batch vs persistent sessions

**Batch (text-to-image, audio-to-text, LLM, etc.):** Each request is independent. The gateway selects an orchestrator, sends the request, receives the response, and the session ends. The next request may go to a different orchestrator.

**Persistent (`live-video-to-video`):** The gateway selects an orchestrator at stream start and routes all frames to the same orchestrator for the stream's duration. The `LiveVideoToVideo` object holds the session state: `publish_url`, `subscribe_url`, `control_url`, and the `PaymentSession` that generates per-segment PM tickets.

If the orchestrator fails mid-stream, the gateway must re-select and establish a new session. In go-livepeer this happens automatically. In custom gateways, the caller catches the error, calls `cursor.next()`, and re-initialises the session.
