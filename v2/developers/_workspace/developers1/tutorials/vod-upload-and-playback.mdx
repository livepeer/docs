This tutorial runs go-livepeer in broadcaster mode on Arbitrum One, sends a VOD file through it, and plays the HLS output back in `@livepeer/react`. The network does the transcoding work; the Gateway pays for it in probabilistic micropayment tickets settled on Arbitrum.

A hosted alternative exists (Livepeer Studio) and absorbs every operational concern below. The Studio version of this workflow is documented in <LinkArrow href="/v2/solutions/studio" label="Studio paths" newline={false} />.

<CustomDivider />

## Prerequisites

- A Linux host or Docker Desktop. CPU transcoding is enough; GPU adds throughput.
- An Ethereum keystore funded with a small Arbitrum One ETH balance. A few dollars covers the tutorial. Network costs run through Probabilistic Micropayments; gas is for ticket redemption and only paid by the redeemer.
- An Arbitrum One RPC endpoint. Alchemy, Infura, or any other Arbitrum RPC provider works.
- Node.js 20 or later, npm
- A short MP4 file (under 100 MB for fast iteration)
- A directory for transcoded output. The Gateway writes to local disk by default; for production, configure S3 or IPFS instead.

## Run the Gateway

```bash icon="terminal"
docker run --rm \
  -p 8935:8935 \
  -v $(pwd)/data:/data \
  -v $(pwd)/keystore:/keystore:ro \
  livepeer/go-livepeer:master \
  -broadcaster \
  -network arbitrum-one-mainnet \
  -ethUrl https://arb1.arbitrum.io/rpc \
  -ethPassword "$ETH_PASSWORD" \
  -ethKeystorePath /keystore \
  -dataDir /data \
  -httpAddr 0.0.0.0:8935 \
  -maxPricePerUnit 3000
```

The flags resolve as follows:

- `-network arbitrum-one-mainnet` switches the Gateway to the production chain.
- `-ethUrl` is your Arbitrum RPC endpoint.
- `-ethKeystorePath` and `-ethPassword` give the Gateway access to the wallet that funds it.
- `-maxPricePerUnit` is the ceiling the Gateway will pay in wei per pixel. Network-typical values move; query current pricing via the Livepeer Explorer before locking in.

Health check:

```bash icon="terminal"
curl http://localhost:8935/status
```

A healthy Gateway responds with JSON describing the node version, ETH address, and current Orchestrator pool.

## VOD Submission

go-livepeer's broadcaster-mode VOD endpoint accepts an HTTP POST of the source file. The exact route varies by go-livepeer version; check the running Gateway's `/status` output or the `cmd/livepeer/starter/starter.go` source on `livepeer/go-livepeer` at the commit you pulled. For the master image at the time of writing, the route is `POST /vod`:

```bash icon="terminal"
curl -X POST http://localhost:8935/vod \
  -F "input=@./source.mp4" \
  -F 'profiles=[{"name":"720p","width":1280,"height":720,"bitrate":3000000,"fps":30}]'
```

The response includes a job identifier the Gateway uses to track the transcode:

```json icon="terminal"
{
  "jobId": "abc123...",
  "status": "submitted"
}
```

<CustomDivider />

## Polling for Completion

The Gateway exposes the job state. Poll until `status` is `completed`:

```bash icon="terminal"
JOB_ID="abc123..."

while true; do
  STATUS=$(curl -s "http://localhost:8935/vod/$JOB_ID" | jq -r '.status')
  echo "$STATUS"
  if [ "$STATUS" = "completed" ] || [ "$STATUS" = "failed" ]; then break; fi
  sleep 2
done
```

A completed response includes the playback manifest URL:

```json icon="terminal"
{
  "jobId": "abc123...",
  "status": "completed",
  "playbackUrl": "http://localhost:8935/vod/abc123/index.m3u8"
}
```

If your installed go-livepeer version uses different paths, the same fields appear under different routes; the source of truth is the Gateway binary you are running.

## Playback

Scaffold a Next.js app and install `@livepeer/react`:

```bash icon="terminal"
npx create-next-app@latest livepeer-vod-app \
  --typescript --tailwind --app --src-dir --import-alias "@/*"
cd livepeer-vod-app
npm install @livepeer/react
```

Replace `src/app/page.tsx`:

```tsx icon="terminal"
'use client';

import { Player } from '@livepeer/react';

const PLAYBACK_URL = process.env.NEXT_PUBLIC_PLAYBACK_URL!;

export default function Home() {
  return (
    <main className="min-h-screen p-8 max-w-3xl mx-auto">
      <h1 className="text-2xl font-semibold mb-4">Livepeer VOD</h1>
      <Player.Root src={PLAYBACK_URL}>
        <Player.Container className="aspect-video rounded overflow-hidden bg-black">
          <Player.Video className="w-full h-full" />
          <Player.Controls />
        </Player.Container>
      </Player.Root>
    </main>
  );
}
```

Set `.env.local`:

``` icon="terminal"
NEXT_PUBLIC_PLAYBACK_URL=http://localhost:8935/vod/abc123/index.m3u8
```

Run the app:

```bash icon="terminal"
npm run dev
```

Open `http://localhost:3000`. The player loads the HLS manifest from the Gateway and plays the transcoded output.

## Storage

The Gateway writes transcoded segments to its `-dataDir` by default. That is fine for local development; it is wrong for production. Three production options:

**S3-compatible storage.** Pass `-objectStore s3://bucket-name` and credentials via environment variables. The Gateway writes segments to S3 and returns S3-backed URLs in the playback manifest.

**IPFS.** The Gateway can pin to an IPFS service. Configure via a webhook handler that receives finished segments and pins them; the recipe is the same shape as S3 with a different pinning client. See <LinkArrow href="/v2/developers/guides/video/storage-and-archival" label="Storage and archival" newline={false} />.

**Gateway-local.** Acceptable for a single-host deployment behind a CDN. The Gateway disk becomes the origin.

<CustomDivider />

## Codecs

The example above transcodes a single 720p H.264 rendition. The network supports a wider profile set: 240p, 360p, 480p, 720p, 1080p at H.264, plus HEVC and AV1 where Orchestrators offer those capabilities. Codec availability varies by Orchestrator. See <LinkArrow href="/v2/developers/build/codec-support" label="Codec support" newline={false} /> for current network coverage.
