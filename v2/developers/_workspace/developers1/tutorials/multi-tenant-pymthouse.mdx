<CustomDivider />

PymtHouse is the open-source clearinghouse for Livepeer applications. It runs the OIDC issuer that authenticates end users, mints scoped JWTs your backend forwards to PymtHouse services, and exposes a wei-denominated billing API so you can attribute usage per user and per app. PymtHouse is hosted at `pymthouse.com` and self-hostable from `github.com/eliteprox/pymthouse`. Canonical API documentation lives at `docs.pymthouse.com`.

The architectural pattern PymtHouse implements is documented in <LinkArrow href="/v2/developers/guides/payments/clearinghouse-pattern" label="Clearinghouse pattern" newline={false} />. This tutorial wires an app against the running platform.

<CustomDivider />

## Prerequisites

- Node.js 20 or later, or `curl` and `jq`
- A registered developer app in PymtHouse. Each app has two OIDC clients: a public `app_…` client (no secret, used in user-facing flows) and a confidential `m2m_…` client (with a `pmth_cs_…` secret, used for server-to-server Builder API calls). Create both from the PymtHouse dashboard.
- The PymtHouse deployment URL. For the hosted instance, the OIDC issuer is `https://pymthouse.com/api/v1/oidc`. For local development, the issuer is `http://localhost:3001/api/v1/oidc`.

Environment variables used throughout:

```bash icon="terminal"
export BASE_URL="https://pymthouse.com"
export PUBLIC_CLIENT_ID="app_yourClientId"
export M2M_ID="m2m_yourClientId"
export M2M_SECRET="pmth_cs_yourSecret"
```

Store the M2M credentials in your backend secret manager. Never expose them to a browser, mobile app, or CLI.

<CustomDivider />

## Two-Client Model

Every PymtHouse-registered app has two OIDC clients:

| Role | ID prefix | Secret | Where it appears |
|---|---|---|---|
| Public | `app_…` | None | Device and browser flows, user-facing URLs, the `client_id` claim in minted user JWTs |
| Confidential (M2M) | `m2m_…` | `pmth_cs_…` | Builder API calls from your backend, RFC 8693 token exchange |

Scopes are configured on each client separately. The public client carries `sign:job` and optionally `users:token`. The M2M client carries `users:read`, `users:write`, `users:token`, and `device:approve` as needed. Request only the scopes each call requires.

The presence of `users:token` on the **public** client controls billing mode: with it, usage is attributed per end user; without it, usage rolls up to the app.

## Machine Token

The backend exchanges M2M credentials for a short-lived access token using the OAuth 2.0 client credentials grant (RFC 6749, section 4.4):

```bash icon="terminal"
MACHINE_TOKEN=$(curl -sS \
  -d "grant_type=client_credentials" \
  -d "client_id=${M2M_ID}" \
  -d "client_secret=${M2M_SECRET}" \
  -d "scope=users:write users:token" \
  "${BASE_URL}/api/v1/oidc/token" | jq -r '.access_token')
```

The response is a JSON object with `access_token`, `expires_in`, and `scope`. Request `users:write` to provision users and `users:token` to mint user JWTs. Scopes are validated against the M2M client's `allowed_scopes`; missing scopes return `400 invalid_scope`.

In production, cache the machine token in memory for the duration in `expires_in` and refresh before expiry. Re-issuing on every request adds an unnecessary round trip.

## User Provisioning

Create or upsert a user record keyed by `externalUserId`. The endpoint is idempotent: sending the same `externalUserId` returns the existing record instead of creating a duplicate.

```bash icon="terminal"
curl -sS \
  -H "Authorization: Bearer ${MACHINE_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "externalUserId": "user-123",
    "email": "alice@example.com",
    "status": "active"
  }' \
  "${BASE_URL}/api/v1/apps/${PUBLIC_CLIENT_ID}/users"
```

A `200` response confirms the user exists in the app's tenant. `externalUserId` is your stable join key between your application and PymtHouse; store nothing else from the response.

<CustomDivider />

## User-Scoped JWT

Mint a short-lived JWT scoped to a specific end user and capability. The token's `sub` is the PymtHouse app-user record id; the `client_id` and `azp` claims are the public `app_…` id. The requested scope is validated against the public client's `allowed_scopes`.

```bash icon="terminal"
USER_JWT=$(curl -sS \
  -H "Authorization: Bearer ${MACHINE_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{ "scope": "sign:job" }' \
  "${BASE_URL}/api/v1/apps/${PUBLIC_CLIENT_ID}/users/user-123/token" \
  | jq -r '.access_token')
```

Forward this JWT to PymtHouse services in the `Authorization: Bearer` header on behalf of the user. The JWT is the only credential the user-facing path ever carries; the M2M secret never leaves the backend.

## Node Backend

A complete backend skeleton in TypeScript:

```ts icon="terminal"
import 'dotenv/config';

const {
  BASE_URL,
  PUBLIC_CLIENT_ID,
  M2M_ID,
  M2M_SECRET,
} = process.env;

let cachedMachineToken: { token: string; expiresAt: number } | null = null;

async function getMachineToken(): Promise<string> {
  if (cachedMachineToken && cachedMachineToken.expiresAt > Date.now() + 30_000) {
    return cachedMachineToken.token;
  }

  const body = new URLSearchParams({
    grant_type: 'client_credentials',
    client_id: M2M_ID!,
    client_secret: M2M_SECRET!,
    scope: 'users:write users:token',
  });

  const res = await fetch(`${BASE_URL}/api/v1/oidc/token`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body,
  });
  if (!res.ok) throw new Error(`token ${res.status}`);
  const json = await res.json();

  cachedMachineToken = {
    token: json.access_token,
    expiresAt: Date.now() + json.expires_in * 1000,
  };
  return json.access_token;
}

async function provisionUser(externalUserId: string, email: string) {
  const token = await getMachineToken();
  const res = await fetch(
    `${BASE_URL}/api/v1/apps/${PUBLIC_CLIENT_ID}/users`,
    {
      method: 'POST',
      headers: {
        Authorization: `Bearer ${token}`,
        'Content-Type': 'application/json',
      },
      body: JSON.stringify({ externalUserId, email, status: 'active' }),
    }
  );
  if (!res.ok) throw new Error(`provisionUser ${res.status}`);
  return res.json();
}

async function mintUserJwt(externalUserId: string, scope = 'sign:job') {
  const token = await getMachineToken();
  const res = await fetch(
    `${BASE_URL}/api/v1/apps/${PUBLIC_CLIENT_ID}/users/${externalUserId}/token`,
    {
      method: 'POST',
      headers: {
        Authorization: `Bearer ${token}`,
        'Content-Type': 'application/json',
      },
      body: JSON.stringify({ scope }),
    }
  );
  if (!res.ok) throw new Error(`mintUserJwt ${res.status}`);
  return res.json();
}

// Drive the flow.
await provisionUser('user-123', 'alice@example.com');
const { access_token } = await mintUserJwt('user-123');
console.log('User JWT:', access_token.slice(0, 40) + '...');
```

## Billing Summary

Read the current billing period, plan, usage totals, daily timeline, and overage in a single call. This endpoint uses HTTP Basic auth with the M2M credentials, not a Bearer token.

```bash icon="terminal"
curl -sS \
  -u "${M2M_ID}:${M2M_SECRET}" \
  "${BASE_URL}/api/v1/apps/${PUBLIC_CLIENT_ID}/billing" | jq .
```

The response is a single snapshot:

```json icon="terminal"
{
  "clientId": "app_yourClientId",
  "plan": {
    "id": "plan-uuid",
    "type": "subscription",
    "name": "Pro",
    "priceAmount": "49.00",
    "priceCurrency": "USD",
    "includedUnits": "100000",
    "overageRateWei": "1000000000000",
    "status": "active"
  },
  "subscription": {
    "id": "sub-uuid",
    "status": "active",
    "currentPeriodStart": "2026-04-01T00:00:00.000Z",
    "currentPeriodEnd": "2026-04-30T23:59:59.999Z"
  },
  "cycle": {
    "periodStart": "2026-04-01T00:00:00.000Z",
    "periodEnd": "2026-04-30T23:59:59.999Z",
    "usage": {
      "requestCount": 8420,
      "totalFeeWei": "8420000000000000",
      "totalUnits": "108300"
    },
    "timeline": [
      { "date": "2026-04-01", "requestCount": 310, "feeWei": "310000000000000" },
      { "date": "2026-04-02", "requestCount": 0, "feeWei": "0" }
    ],
    "overage": {
      "overageUnits": "8300",
      "overageWei": "8300000000000000"
    }
  },
  "platformCutPercent": 10
}
```

Every `*Wei` field is a decimal string, not a number. Values exceed `Number.MAX_SAFE_INTEGER`. Parse with `BigInt` and format for display only at the boundary:

```ts icon="terminal"
const wei = BigInt(response.cycle.usage.totalFeeWei);
const eth = Number(wei) / 1e18;
console.log(`${eth.toFixed(6)} ETH`);
```

The `timeline` array contains one entry per calendar day in the period, with zero-fill for days without usage. When `subscription` is `null` the period falls back to the current UTC calendar month. When `plan` is `null` no plan is configured; surface this as a UI state, not an error.

For per-user attribution, query the Usage API at `GET /api/v1/apps/{clientId}/usage` (documented in the PymtHouse repo at `docs/builder-api.md`).

## Common Errors

**`400 invalid_scope`.** The scope requested in the client credentials grant is not in the M2M client's `allowed_scopes`. Add the scope to the M2M client in the PymtHouse dashboard.

**`401` on user token mint.** The scope requested in the user-token call is not in the public client's `allowed_scopes`. Add the scope to the public client, not the M2M client.

**`404` on the billing endpoint.** Either the credentials are valid but belong to a different app, the path `clientId` does not resolve, or no authenticated principal is present. PymtHouse returns `404` for all three to prevent app-id enumeration.

**Mismatched IDs.** `PUBLIC_CLIENT_ID` must be the `app_…` id throughout the URL path. The `m2m_…` id is only used in the token endpoint body and Basic auth. Cross-wiring these surfaces as `401` or `404`.

<CustomDivider />

## Discovery

PymtHouse publishes endpoint paths through OIDC discovery. Read endpoints at runtime so your integration tracks rotations automatically:

```bash icon="terminal"
curl -sS "${BASE_URL}/api/v1/oidc/.well-known/openid-configuration" | jq .
```

The `token_endpoint`, `jwks_uri`, `issuer`, and other standard OIDC fields are returned. Validate every JWT against `jwks_uri` at request time. Embedding a key in your codebase breaks on rotation.
