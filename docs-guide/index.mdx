# Docs Guide

Livepeer Docs is a **self-remediating, ownerless documentation operating system**. 1,128 published MDX pages stay fresh through 59 GitHub workflows, 341 typed scripts, and 35 portable AI skills. Ten audience tabs render from canonical sources via a zero-duplication wrapper pattern. The whole repo is legible to humans, AI agents, and automation, governed by a four-part contract, and contributable without staff context.

<Note>
**What this is.** A docs platform that builds and validates itself.
- **AI-native** – `llms.txt`, an AI sitemap, a hosted MCP endpoint, six native agent adapters, a Mintlify chat assistant.
- **Self-remediating** – validators detect drift; remediators repair it; generators rebuild derived artefacts; audits surface the rest as backlog.
- **Ownerless by contract** – every governed surface declares a canonical source, a deterministic validator, an exact repair command, and a single gate layer.
- **Contributor-friendly** – one `lpd` CLI wraps setup, scoped preview, staged tests, repair, and governed page moves.
</Note>

## Contributor quickstart

<Tip>
Five steps from clone to first PR. The correct workflow is the easiest workflow – every step routes through `lpd`, which installs the hooks, validators, and scoped preview that match what CI runs.
</Tip>

<Steps>
  <Step title="Clone and switch to the production branch">
    ```bash icon="terminal"
    git clone https://github.com/livepeer/docs.git
    cd docs
    git checkout docs-v2
    ```
    `docs-v2` is the production branch that deploys to `docs.livepeer.org`. `docs-v2-dev` is the internal working branch for in-flight work. Public contributors branch from and PR against `docs-v2`.
  </Step>
  <Step title="Run setup">
    ```bash icon="terminal"
    bash lpd setup --yes
    ```
    Installs git hooks, dependencies, and optionally puts the CLI on your `$PATH`. Non-interactive when `--yes` is set.
  </Step>
  <Step title="Confirm your environment">
    ```bash icon="terminal"
    lpd doctor
    ```
    Reports Node/PATH/Mintlify/Puppeteer/hooks status. Fails fast if anything is missing.
  </Step>
  <Step title="Boot a scoped preview">
    ```bash icon="terminal"
    lpd dev --scoped --scope-tab Developers
    ```
    A filtered Mintlify dev server against a 1,128-page nav boots in ~2 seconds instead of ~10 minutes. Pick any tab name, prefix, or fuzzy match (`Orch`, `Resources`, `Gate`, etc.).
  </Step>
  <Step title="Edit, validate, commit, PR">
    ```bash icon="terminal"
    # create a feature branch from docs-v2
    git checkout -b docs/<descriptive-slug>

    # edit your MDX or JSX file
    lpd test --staged      # same checks CI runs, but only on your changes
    git commit -m "<scope>: <change>"
    git push origin docs/<descriptive-slug>
    gh pr create --base docs-v2
    ```
    Pre-commit hooks run MDX render checks, allowlist guards, redirect integrity, and no-deletion enforcement in under 60 seconds. PR CI re-runs the blocking checks against changed files.
  </Step>
</Steps>

For the complete contributor flow with branching conventions, override trailers, governance approval labels, and the canonical PR template, read [contributing/contributing.mdx](/docs-guide/contributing/contributing).

## Docs philosophy

Three operating principles shape every decision in this repo. They are the answer to *why* a docs site needs 59 workflows, an `AGENTS.md`, and a four-part ownerless contract.

<AccordionGroup>
  <Accordion title="Documentation Is Infrastructure" icon="screwdriver-wrench">
    Docs are not editorial output. They are infrastructure: maintained under load, degrading without active governance, requiring testing, automation, and versioning. The Stack Overflow podcast *Your Docs Are Your Infrastructure* (Fabrizio Ferri-Benedetti, November 2024) reframed how this engagement was scoped.

    Operationally that means the 59-workflow CI suite, 341 governed scripts, `lpd` CLI, component library, content pipeline, and `docs-guide/` governance system are all part of the deliverable. They are the scaffolding that makes every page reliable, maintainable, and improvable by anyone – not just by maintainers who built it.

    **Locked by:** [Infrastructure principles](/docs-guide/policies/infrastructure-principles) · [Source-of-truth policy](/docs-guide/policies/source-of-truth-policy).
  </Accordion>
  <Accordion title="AI Is the New Search" icon="brain-circuit">
    For over a decade, SEO drove documentation discoverability. That paradigm is being displaced. LLMs index, summarise, and recommend infrastructure products at scale. Developers begin research in ChatGPT, Claude, Perplexity, or Gemini before they hit Google. Docs are being read, evaluated, and cited by machines before they reach humans.

    The implication is structural, not cosmetic. Semantic headings, stable canonical URLs, machine-readable frontmatter, OpenAPI integration, and an [`llms.txt`](https://docs.livepeer.org/llms.txt) at repo root are the new minimum-viable distribution layer. Answer Engine Optimisation (AEO) is the evolution of SEO for this era. This repo builds Livepeer's AEO layer from first principles.

    **Surfaces:** `/llms.txt`, `/sitemap-ai.xml`, hosted MCP at `docs.livepeer.org/mcp`, the Mintlify chat assistant configured by `.mintlify/Assistant.md`.
  </Accordion>
  <Accordion title="Agents Are the New Users" icon="robot">
    AI agents query documentation to generate code, answer support tickets, configure infrastructure, and build integrations without human intervention. Agents need docs that are not merely readable but executable – with explicit preconditions, invariants, verification steps, and failure modes.

    Six native adapters (Claude, Cursor, Windsurf, Augment, Codex, Copilot) all root in a single [`AGENTS.md`](https://github.com/livepeer/docs/blob/docs-v2/AGENTS.md) baseline. The [`Get AI to set up the gateway`](/v2/gateways/quickstart/AI-prompt) page is a direct instantiation: a doc written for AI agent consumption, not human browsing. Agents run the same validators humans run, with no escalation path.

    **Surfaces:** `AGENTS.md`, native adapters in `.claude/`, `.cursor/`, `.windsurf/`, `.augment/`, `.codex/`, `.github/`, the 35-skill catalogue at `ai-tools/ai-skills/`, and per-page AI companion JSON.
  </Accordion>
</AccordionGroup>

## Docs personas

Every page in this repo is designed for one of four readers. Each gets a different entry point and a different default surface.

<CardGroup cols={2}>
  <Card title="Reader" icon="book-open" href="/v2/home/test">
    Lands on `docs.livepeer.org`. Searches, asks the chat assistant, or downloads `llms.txt` to feed an LLM. Never needs to know that 35 AI skills exist – but benefits from them every time the contracts page is fresh, the changelog is current, and the API reference matches the spec.
  </Card>
  <Card title="Contributor" icon="code-pull-request" href="/docs-guide/contributing/contributing">
    Opens an issue using one of nine templates, edits a page, runs `lpd dev`, submits a PR. The PR template auto-fills with Required Reading per changed-path globs. Pre-commit hooks catch drift in seconds. No maintainer review needed for routine drift.
  </Card>
  <Card title="Maintainer" icon="user-gear" href="/docs-guide/policies/ownerless-governance">
    Owns a governed surface (component library, scripts, contracts pipeline, AI skills…). Authors policy in `policies/`, registers validators in `operations/governance/config/`, and watches the decisions registry. Routine drift is handled by the contract – humans handle policy authorship and destructive operations.
  </Card>
  <Card title="AI agent" icon="robot" href="/docs-guide/contributing/agent-instructions">
    Reads `AGENTS.md`, follows the native adapter for its IDE, runs the same gates humans run. The `task-contract.yaml` declares scope-in/scope-out; lock files prevent overlap. The cross-agent packager distributes the same 35 skills to every agent.
  </Card>
</CardGroup>

### GitHub Actions and automations

**What it delivers.** The repo's operating system. 59 workflows on a strict 7-prefix taxonomy (`validator-`, `generator-`, `integrator-`, `remediator-`, `audit-`, `dispatch-`, `interface-`). 341 typed scripts under `operations/scripts/`. Every script declares type/concern/niche via an 11-tag JSDoc header. Five-tier gate model: pre-commit (local, ≤60s budget), pre-push (Codex contract), PR CI (blocking, changed-file scope), scheduled CI (broad sweeps), manual dispatch (repair waves). Workflow YAML files are dispatchers only – business logic lives in the typed scripts.

### Adaptive architecture (the flagship)

**What it delivers.** The repo's self-remediation model. Every governed surface declares a four-part contract – canonical source · deterministic validator · exact repair command · single gate layer. When any of those four is missing, the surface stays `advisory` until the contract is complete. Once complete, an OSS contributor – or an AI agent acting on their behalf – can correct routine drift without privileged context. The five-stage control loop runs continuously: **detect** via validators, **explain** via policy documents and printed remediation messages, **repair** via remediators or `lpd repair`, **verify** by re-running the validator, **record** into reports, catalogues, and the decisions registry.

|---|---|---|
| Validators | 49 | `operations/scripts/validators/` |
| Remediators | 29 | `operations/scripts/remediators/` |
| Generators | 30 | `operations/scripts/generators/` |
| Audits (read-only) | 21 | `operations/scripts/audits/` |
| Generated artefacts (registered) | 29 | `operations/governance/config/generated-artifacts.json` |
| Ownerless-ready surfaces | 8 | `operations/governance/config/ownerless-governance-surfaces.json` |
| Surfaces in broader registry | 28 | `operations/governance/config/repo-governance-surfaces.json` |

Deep dive: [Adaptive architecture](/docs-guide/features/adaptive-architecture).

<Note>
**Honest caveat.** The model is "ownerless for routine drift" – not "ownerless for policy authorship or destructive operations." Eight surfaces are formally contracted today; 20 more are advisory. Promoting one of those to ownerless-ready is the most repeatable contribution path in this repo.
</Note>

## Ownerless repo management

How the repo intends to be ownerless in practice. The pieces below are wired today; gaps are surfaced as community-help opportunities.

<Steps>
  <Step title="Open an issue using a template">
    `.github/ISSUE_TEMPLATE/` ships nine templates: bug report, docs page issue, feature request, content request, tooling/CI issue, question/clarification, plus config, docs-review, and feature-internal. Each template auto-applies the correct `area:*` and `priority:*` labels.
  </Step>
  <Step title="Required Reading auto-fills in the PR template">
    The pull-request template includes a `## Required Reading` section that gets auto-populated by `check-canonical-citation.js` from changed-path globs in `operations/governance/config/required-citations.json`. Merge is blocked until the contributor ticks the listed framework. Locked by [D-DG-12](/docs-guide/decisions/docs-guide-structure).
  </Step>
  <Step title="Reviewers and Copilot auto-assign">
    `interface-*` workflows assign reviewers based on `area:*` labels and CODEOWNERS. Copilot is auto-assigned to governance-tagged issues for first-pass repair.
  </Step>
  <Step title="Discord intake becomes a governed issue">
    A repository_dispatch pipeline (`interface-copy-intake-discord-issues.yml`) routes community questions from Discord into the issue queue with the right labels and references.
  </Step>
  <Step title="Decisions get IDs, not lore">
    Every architectural decision lives in [`docs-guide/decisions/`](/docs-guide/decisions/registry) with an ID grammar `D-{SCOPE}-{NN}`. The master registry indexes all per-domain logs. "Decisions made in chat that aren't written here don't exist" is enforced by convention.
  </Step>
</Steps>

## Authority tiers

Files in `docs-guide/` follow a six-tier precedence model. When two governance docs disagree, the higher tier wins. Every file declares its tier in the `authority:` frontmatter field.

| Tier | Folder | What it holds | Example |
|------|--------|---------------|---------|
| T0 | `decisions/` | Locked precedent with IDs and supersession chains | [D-DG-01..13: docs-guide structure](/docs-guide/decisions/docs-guide-structure) |
| T1 | `policies/` | Enforced rules; each policy declares consumers and a validator | [Source-of-truth policy](/docs-guide/policies/source-of-truth-policy) |
| T2 | `frameworks/` | Subject models, taxonomies, lifecycles | [Component framework](/docs-guide/frameworks/component-framework-canonical) |
| T3 | `standards/` | Rules about form (voice, frontmatter, naming) | [Voice and copy](/docs-guide/standards/voice-and-copy) |
| T4 | `contributing/` | Procedures (how to do work) | [Contributing](/docs-guide/contributing/contributing) |
| T5 | `reference/`, `catalog/` | Look-up only, never normative | [Feature map](/docs-guide/features/feature-map) (under `features/` today; moves to `reference/features/` per D-DG-03) |

Adapter files (`AGENTS.md`, `.claude/CLAUDE.md`, `.github/AGENTS.md`, `.cursor/rules/`, `.windsurf/rules/`, `.augment/rules/`) point UP into `docs-guide/`. They surface canonical truth for specific consumers but hold no authority. Any rule stated only in an adapter file is invalid and must canonicalise into a T0–T3 source. Locked by [D-DG-11](/docs-guide/decisions/docs-guide-structure).

## Update rules

1. Update manual docs when behaviour, process, canonical boundaries, or architecture changes. Bump `lastVerified` on save.
2. Regenerate generated catalogs when scripts, workflows, or templates change:
   - `node operations/scripts/generators/governance/catalogs/generate-docs-guide-indexes.js --write`
   - `node operations/scripts/generators/governance/catalogs/generate-docs-guide-pages-index.js --write`
   - `node operations/scripts/generators/governance/catalogs/generate-docs-guide-components-index.js --write`
   - `node operations/scripts/generators/components/library/generate-ui-templates.js --write`
   - `node operations/tests/unit/script-docs.test.js --write --rebuild-indexes`
   - `node operations/scripts/validators/content/structure/enforce-generated-file-banners.js --check`
3. Re-run the docs audit pipeline when docs, scripts, reports, or routing paths change:
   - `node operations/scripts/dispatch/governance/repo/repo-audit-orchestrator.js --mode static --scope full`
   - `node operations/scripts/integrators/ai/agents/cross-agent-packager.js --agent-pack all`
4. Keep `README.md` high-level. Link to canonical docs-guide pages for deep detail.
5. Keep generator scripts, generated outputs, and downstream consumers in sync whenever a catalog path or title changes. Use the `/propagate` skill on any move or rename of a file with more than five incoming references.
